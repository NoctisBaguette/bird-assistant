# 地图、头像与社区边界评阅 v0.11

日期：2026-10-30（Asia/Shanghai）。[English counterpart](en/11-map-profile-community-design.md)。这是浏览器前端检查点；微信原生开发尚未开始，地图、账号与公开活动仍为演示。

## 开发与 GitHub 工作方式

用户计划在进入微信开发者工具阶段时使用独立仓库 `NoctisBaguette/bird-assistant-miniprogram`，保留完整项目代码和版本历史。本轮不创建仓库、不开始原生实现；截图中的仓库名和描述可沿用，是否公开由用户决定。

后续约定：首次 clone 后，在微信开发者工具中导入同一个本地目录。经过验证的版本进入稳定分支 `main`，每轮交付附提交号、改动、实际检查、未验证项和升级说明；用户检查本地修改后执行 `git pull --ff-only origin main`，再编译和真机预览。若有本地改动或分叉，先保留并解决，不使用 reset 或强制覆盖。实验工作在功能分支，避免用户拉到半成品。

迁移时保留当前可运行前端及设计/QA/累计日志的来源记录，不复制无关后端、凭据、机器缓存或他人未提交修改。项目仍使用待定的非 OpenAI 服务；不提交密钥。原生目录结构、AppID 配置和依赖安装步骤在实际建仓时确定，届时提供精确命令，当前不虚构已有仓库或可运行的小程序。

## 头像：自己的图片和默认图库

- 上传 JPG、PNG 或 WebP，在本地读取，设备原件不修改、不上传。
- 图片进入同一个裁剪页：拖动、缩放、左右移动、上下移动、90° 旋转、重置；圆形遮罩显示最终头像范围，滑杆提供拖动之外的操作方式。
- 确认裁剪仅更新资料草稿；保存资料才更新当前个人头像，取消修改保留旧头像。重新裁剪可恢复原来的处理副本和参数。
- 六个自有代码插画头像可直接选择：夜枭、林雀、绿叶、山岚、湖光、名字首字；不依赖第三方头像图片。
- 浏览器保护值为 20 MB、解码后 4000 万像素；处理副本最长边 2048，输出 512×512 JPEG。这些是当前本地头像演示的实现参数，不是鸟类素材上传的正式限制。读取、解码失败或过大时旧头像保留；迟到的读取结果不能覆盖另一份资料草稿。
- 真实账号上传、资源存储、跨设备同步和微信头像接口另行接入。普通观察/资料仍为会话演示，不承诺刷新后头像保留。

## 地图：按用户在看的范围组织信息

定位按钮之前只把平移量归零，但示例位置本身位于画布下方。本轮改为根据该点的实际画布坐标、画布尺寸和缩放求平移，使位置点落在地图视口中心。缩放保留中心对应的地理示意点，不再把归零误当作居中。真实定位权限被拒绝时仍可手动浏览。

区域卡采用地图视口中心，而不是底部卡片中心或一直固定的“湖畔公园”。平移过程中每帧刷新候选区域，距离按 5:8 示意画布比例计算，边界上保留当前区域，只有新区域明显更近才切换，减少抖动。当前只有湖畔/林间两个虚构区域；真实地图阶段改用地点/行政区覆盖、距离、缩放级别和无覆盖状态，不能把演示算法直接当作完整地理服务。

搜索建议随输入更新，空输入可查看六个推荐示例地点；最多显示三行，额外结果在面板内上下滚动，不撑满地图。支持中文/英文匹配、方向键、回车、Esc、无结果提示。列表滚动不触发地图缩放。选中结果后定位该点并打开地点详情；详情高度限制为视口的 45%，选中标记留在详情上方。

底部区域卡向下移，为中央导航按钮保留间隙。目前仍显示缩小的“示意地图”标记，移到上部，不占底部卡片空间。**接入真实地图后移除该演示标记，但保留地图供应商要求的归属信息；区域卡再利用释放的空间调整。** 不在仍为假地图时提前删除真实性标记。

## 地点收藏与打卡

按本轮用户要求，地点收藏和打卡均设计为公开活动，使用“公开收藏 / 公开打卡”明确文案。首次操作先展示名称、地点和公开范围，确认后才增加活动；再次点击可以撤回。发生模拟发布失败时不增加计数，可重试或取消。

公开活动仅关联用户和所选地点，不自动附加私人照片、观察、实时定位或轨迹。远程从搜索结果填写的打卡标为“用户填写、未核验”，不伪装为到访证明。以后如需要“核验到访”，必须另行设计定位权限、误差、时间窗口和无法定位时的降级。

“我的 → 地点收藏与打卡”可以重新打开地点。这里与原有“保存他人内容”的私人书签、本人鸟种收藏、地图观察发布分别管理；收藏地点不增加鸟种数，打卡也不发布一条鸟类观察。本轮没有真实账号间共享或公开服务，仅演示对应状态。

## 徽章与成长：建议现在定目的，第一版做轻

本轮扩展讨论页，没有接入真实奖励。建议先鼓励：初次保存自己的观察、记录行为或环境线索、完成第一份手帐；私人记录与待鉴定记录同样有效。重复编辑同一条记录不重复计奖。徽章不等于鉴定正确、专家资质或统计上的可靠性。

观鸟庭院、羽叶和知识练习保留为后续候选，不提前固定等级和积分数值。不以稀有鸟、公开精确地点、打卡次数、发帖/点赞量排名，不设断签惩罚，不迫使用户公开记录。知识练习的内容与答案来源、重复奖励、已删除记录如何处理，还需单独确认。

## 私聊与群聊：建议现在定流程，消息服务分期实施

本轮扩展讨论页，不提供会伪装发送成功的按钮。建议私聊先限双向好友；陌生人消息请求是否开放另行决定。群聊以一次约鸟/小型活动为目标，邀请加入，明确管理员、静音、退群、移除成员与举报/屏蔽。好友关系不自动加群或开放私人记录。

消息状态至少区分待发送、已发送和失败重试；未读、离线恢复、去重、历史消息访问、通知、删除与撤回规则均应明确。第一版不承诺已读回执或消息端到端加密。分享观察或手帐需先预览卡片字段，不直接授予私人记录访问权。群活动不默认公布精确位置。

建议顺序：完成地图、识别、手帐和私人保存的稳定链路，再开发真实消息基础设施；成长第一版使用轻量里程碑。此顺序是本轮设计建议，尚不自动成为团队当期验收范围。

四天目标应是范围明确的真机体验版，以下为相对工作日建议，起止日期尚未指定：

1. 第一天：确认 AppID、成员权限和已有技术经验，初始化原生目录、五个 Tab 与基础配置；尽早验证手机运行/上传路径，避免最后一天才发现平台阻碍。
2. 第二天：先打通采集/导入、素材复核、私人记录保存/重开及拒绝权限时的替代路径；错误要保留用户素材。
3. 第三天：地图与搜索、手帐、头像和已经准备好的识别接口；未接通的能力保持明确状态。冻结新增功能。
4. 第四天：集中真机回归、弱网/前后台/权限/缓存/长文本/屏幕适配，修复阻断问题，形成可交给体验者的构建与已知问题清单。完整聊天、复杂庭院、实时多模态优化不塞进首个四天范围。

建议从 DushiSports 项目带回一份“实际踩坑与已验证修复”摘要：工具/基础库/语言版本，目录与编译配置，AppID/开发成员，组件与样式/安全区，云环境/函数部署，登录与数据库权限，图片上传和临时路径，合法域名/请求/真机差异，隐私权限，上传与体验版流程。按触发条件→原错误→根因→实际修复→验证证据整理，区分已解决/未解决/本项目可复用；移除密钥、token 与无关用户数据。该项目资料尚未在本轮读取，不假定上述问题实际发生过，也不默认复用其账号或数据环境。
